# PR #15 고객 공개 전 검토

검토일: 2026-10-15 (KST). 기준: `825ae54ebaaa27bad95632c76304cee2d4c4787c`, Draft, 미병합. 실제 Supabase·운영 데이터·SMTP·배포에는 접근하거나 변경하지 않았습니다. **현재 고객 공개 보류**를 권고합니다. 아래 수정안과 별도로 실제 Supabase 스테이징 검증 및 사업 기준 확정이 남아 있습니다.

## 재현한 결함과 수정

| 우선순위 | 원본 문제 / 재현 | 영향 | 수정안 |
|---|---|---|---|
| P1 | `site/om-config.js`의 `samplo:false`는 화면만 막음. 정상 회원 JWT로 `sp_save_order` 또는 `sp_request_topup`를 직접 호출하면 성공 | SQL이 설치되어 있다면 고객 공개 전에도 예시 기준으로 의뢰·충전 신청 가능. 운영 DB에서 실제 발생했는지는 미확인 | `settings.sp_access.enabled` 기본 false, 누락·문자열 true도 닫힘. 두 접수 RPC에서 서버 검사. 운영자 점검 예외. 화면도 DB 스위치 확인 |
| P2 | 가입 metadata `{"sp_agreed":false}`, `null`, 문자열 `"true"`도 키가 존재해 약관 동의시각 기록 | 동의하지 않은 계정에 동의 기록 생성 | JSON boolean true인 경우에만 기록. 기존 잘못된 기록은 자동 소급 수정하지 않음 |
| P2 | `lpad(nextval(...)::text,4,'0')`는 10000을 `1000`으로 자름 | 같은 월의 기존 1000번 또는 이후 번호와 충돌하여 접수 실패. 시퀀스는 월마다 초기화되지 않음 | 최소 4자리, 큰 번호는 전체 자릿수 유지. 시료 라벨에도 전체 의뢰번호 유지 |
| P2 | 운영자가 `completed → confirmed → cancel` 호출 가능 | 완료 건 취소 금지 검사를 우회하고 charged를 환입할 수 있음. 운영자 권한이 필요한 결함이며 고객의 권한 상승은 아님 | 완료 상태 재개방 차단. 재개방이 필요하면 별도 승인·감사 흐름을 설계해야 함 |

접수 차단은 신규 의뢰·수정·충전 신청을 대상으로 합니다. 기존 내역 조회, 취소, QC 선택을 전부 중단하는 서비스 정지 기능은 아닙니다. 일반 회원에게 운영 RPC의 EXECUTE가 있어도 함수 내부 `is_admin()` 검사로 차단해야 하며, EXECUTE 부여 자체가 운영 권한 부여를 뜻하지 않습니다.

## 실행 결과와 입증 범위

검증 환경: PGlite 0.5.10 / PostgreSQL 18.6 WASM, Supabase auth/storage stub, Chromium 153.0.8010.0, Playwright 1.62.1. 실제 PostgreSQL 16 또는 Supabase 검증 결과로 해석하면 안 됩니다.

| 검증 | 원본 | 수정본 | 한계 |
|---|---|---|---|
| 기존 SQL `flow.sql` | 통과 (109문장) | 통과 (109문장) | stub 기반 |
| 기존 SQL `billing.sql` | 통과 (42문장) | 통과 (42문장) | 실제 결제·세금계산서 발행 아님 |
| 기존 SQL `samplo.sql` | 통과 (196문장) | 통과 (197문장) | 수정본은 테스트에서만 접수 스위치를 켬 |
| 추가 회귀검사 14개 | 7 실패, 7 통과 | 14 통과 | 실패 7개에는 새 private helper가 원본에 없다는 검사 1개 포함 |
| 브라우저 | 원본 466개를 재실행하지 못함 | 390px/1280px에서 36개 화면 점검 + 2개 데이터 흐름 검사 통과 | 모의 인증·전송 계층 + 실제 파일/PGlite. 실제 Supabase 로그인·JWT·PostgREST 검증 아님 |

문장 수는 테스트 assertion 수가 아닙니다. 기존 SQL의 일부 항목은 boolean/행 수를 출력하기만 하므로 실행 성공이 모든 기대값을 자동 입증하지 않습니다. 고객 간 orders/samples/events/ledger/topups 5개 표의 행 수 0, 타 고객 QC 결정·잔액 조정 거부는 추가 회귀검사에서 명시적으로 판정합니다. 소유자·운영자의 정상 조회도 기존 흐름과 브라우저에서 확인했습니다.

PR 설명의 브라우저 466개 검사는 저장소 트리에서 실행 스크립트·결과물·CI 근거를 찾지 못했습니다. 해당 숫자는 작성자의 기록이며 이번 검증으로 재확인한 숫자가 아닙니다.

### 데이터 흐름

1. 가입 화면의 메타데이터 → 모의 auth.users INSERT → profiles 생성과 Samplo 동의시각 기록을 확인했습니다. 이메일 확인·비밀번호 검증은 모의 처리하므로 미검증입니다.
2. 로그인된 고객 세션을 모의 설정 → 회원 정보/동의 확인 → 설정 읽기 → 5단계 의뢰 UI → `sp_save_order` → orders/samples/events 저장을 확인했습니다.
3. 운영자 `sp_confirm_order` → 행 잠금 및 `p_seen` 비교 → 충전금 잔액 검사 → 차감 장부와 확정 상태 저장을 확인했습니다. stale 화면·잔액 부족 시 거절은 기존 SQL 테스트에 포함됩니다.
4. received 상태에서 QC warn → 고객 화면 표시 → 고객 proceed 선택 → decision/decided_at 및 이벤트 저장을 확인했습니다. QC 상태 변경 시 선택 초기화, 같은 상태의 값·메모 수정 시 선택 유지는 기존 SQL 테스트에서 확인했습니다.
5. 운영자 취소 → charged 환입 → charged 0 → 잔액 복구, 충전 신청 UI → 입금 확인 RPC → 원금 적립과 잔액 증가를 확인했습니다. 각 화면 크기에서 이 흐름을 실행했습니다. 금액 예시는 테스트용이며 환불 정책 승인에 해당하지 않습니다.

### 데이터 접근·RPC·입력 검사

- sp_* 표는 RLS를 켜고 authenticated에는 SELECT만 부여합니다. 고객은 본인 주문/하위 시료·이벤트/본인 장부·충전 신청만 조회합니다. 직접 상태·금액·잔액 쓰기는 막힙니다.
- `sp_log`, `sp_balance_of`, `sp_setting`, `log_event`는 원본 PR SQL과 수정 SQL에서 anon/authenticated 직접 EXECUTE가 차단됩니다. 수정 helper `sp_require_open`도 비공개입니다. main에 이 구문이 없었다는 사실만으로 운영 DB의 현재 권한이나 악용 이력을 단정할 수 없습니다.
- 기존 SQL은 서비스·시료 조합, 시료명 중복/형식, 양 범위, 날짜 형식/미래 채취일/수거 한계, 당일 시간대 마감, 연락처, 청구 이메일·사업자번호, 길이 제한 등을 검사합니다. 브라우저와 서버는 별도 구현이므로 같은 설정을 쓴다는 사실만으로 모든 입력에서 동등성이 보장되지는 않습니다.
- 충전 신청 중복은 부분 unique index, 충전 확인은 requested 상태 조건, 차감·음수 조정은 사용자별 advisory lock으로 방어합니다. 다중 연결의 동시성·교착상태 검증은 이번 단일 세션 엔진에서 수행하지 않았습니다.

### 모바일

390×900 및 1280×900에서 가입/인증 안내, 서버 접수 차단, 고객 목록, 의뢰 5단계, 접수 상세, QC 선택, 취소·환입 상세, 충전 신청·완료, 운영 접수/진행/충전금/설정을 확인했습니다. 페이지 전체 가로 넘침과 렌더 오류는 없었습니다. 시료 입력 표는 컨테이너 내부 가로 스크롤을 허용합니다. 한국어 글꼴을 설치한 환경에서도 캡처를 확인했습니다.

터치 실기기, iOS Safari, 가상 키보드에 의한 뷰포트 변화, 모든 접근성·스크린리더 동작은 미검증입니다. 운영 상태 변경은 이 브라우저 테스트에서 RPC로 구동했으며 운영자의 모든 폼 클릭을 자동화한 것은 아닙니다.

## 실제 Supabase에서 공개 전에 필요한 검증

전용 스테이징 프로젝트, 일반 고객 A/B 및 운영자 테스트 계정, 테스트 메일 수신함이 필요합니다. 현재 이 연결 정보·테스트 계정은 제공되지 않았습니다. 운영 DB를 대신 사용하거나 임의로 계정을 생성하지 않았습니다.

| 단계 | 실행할 검증 | 통과 기준 |
|---|---|---|
| 스키마 | 승인된 스테이징에 schema → billing → samplo 적용·재적용 | 기존 데이터 보존, 함수 인자·권한·정책 유지, PostgREST schema cache 반영 |
| 권한 상태 | `audit-live-readonly.sql` 결과 확인 | sp_* RLS 활성화, 고객 직접 쓰기 차단, private helper/log_event 직접 실행 차단 |
| 인증 | 이메일 가입·중복 가입·미인증 로그인·확인 링크·만료 링크·비밀번호 재설정·로그아웃·토큰 만료 | 실제 GoTrue/SMTP/Redirect URL과 화면이 일치. 잘못된 계정으로 권한 부여 안 됨 |
| API 격리 | A/B 각각의 실제 JWT로 5개 표 직접 SELECT 및 쓰기, 다른 고객 ID로 모든 변경 RPC 호출 | 타 고객 행 0, 직접 쓰기 거부, 운영 전용 RPC 거부, 상태·장부 불변 |
| 비공개 접수 | DB false/누락/문자열 true + 브라우저 true, 브라우저 설정 우회 후 직접 RPC | 일반 회원 의뢰·충전 거부, 운영자 점검 가능 |
| 전체 흐름 | 실제 A 가입 → 의뢰 → 운영 확정 → QC → A 결정 → 충전 입금 확인·차감·취소 환입 | UI와 REST/DB의 ID·상태·금액·이벤트 일치, 실제 입금은 사용하지 않고 테스트 장부만 사용 |
| 경합 | 별도 DB 연결에서 같은 충전 2회 확인, 같은 잔액으로 두 주문 확정, 고객 수정 vs 확정, QC 선택 vs 취소/완료 | 중복 적립/이중 차감/음수 잔액/종료 건의 뒤늦은 결정 없음. 충돌 시 재시도 안내 |
| 모바일 | iOS Safari 및 Android에서 320/360/390px, 키보드·표 스크롤·체크박스·수정·재시도 | 필수 버튼·오류·정보 접근 가능, 잘못된 중복 제출 없음 |

실제 프로젝트의 테이블 ACL·추가 정책·사용자 정의 JWT hook·Realtime 설정·메일 제한은 파일만으로 알 수 없습니다. 이 결과만으로 운영 안전성을 승인할 수 없습니다.

## 사업상 결정이 필요한 항목 (미확정)

- 시료별 최소/최대량, 단위, 수거 시간·주말·리드타임·온도·운송 책임. 현재 seed는 예시입니다.
- QC fail/warn에서 그대로 진행 허용 여부, 고객 결정 전 다음 단계로 넘어갈 수 있는지, 재추출·추가 시료의 비용과 재동의 절차. 현재 `sp_set_status`는 중간 단계 건너뛰기와 QC 미결 상태 진행을 막지 않습니다. 이를 임의로 새 정책으로 제한하지 않았습니다.
- 취소 수수료·부분 환불·보너스 반환·현금 인출·완료 후 정정. 현재 취소 RPC는 charged 전액을 장부로 환입합니다. 이 동작을 테스트했으나 정책으로 승인한 것은 아닙니다.
- 충전 단위·상한·보너스율·입금 계좌·청구 방식, 완료 건 재개방 시 승인권자와 감사 기록.
- 개인정보 보유기간·삭제/익명화·운송사 위탁·국외 이전 및 약관 버전별 동의 기록. profiles 삭제 시 주문·충전금 기록이 cascade 삭제되는 현재 구조도 보존 기준과 맞는지 결정해야 합니다.

## 변경·승인 경계

수정안은 검토용 브랜치에만 작성합니다. 운영 DB 변경·스키마 적용·PR 병합·고객 공개·서비스 배포를 하지 않았습니다. 공개 단계는 사업 기준 확정 → 승인된 스테이징 검증 → 결과 검토 → 운영 적용·병합·배포 승인 순서로 진행해야 합니다.
